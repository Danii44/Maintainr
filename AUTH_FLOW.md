# Maintainr Authentication Flow

Maintainr exposes separate `/sign-in` and `/sign-up` entry pages. In the current preview, both pages use the installed Manus OAuth adapter and explicit authorization intent: `/sign-in` uses `type=signIn`, while `/sign-up` uses `type=signUp`. The callback upserts the authenticated identity into the `users` table, creating the account on first authentication and updating the existing record on later sessions.

For independent distribution, replace the Manus OAuth adapter in `server/_core/oauth.ts`, `server/_core/sdk.ts`, and `client/src/main.tsx` with the selected provider’s server-side session adapter. Preserve the exact role values and keep session validation on the server. Do not expose provider secrets in the browser.

After authentication, the exact role is checked by the protected portal route guard. The backend remains authoritative for role, organization, ticket, reminder, and unit scoping; the frontend guard only prevents confusing navigation. A user without the required portal role receives an access message rather than seeing another role’s workspace.

First-time tenants use `/join-unit` after authentication. The tenant enters the six-digit access code generated by a property manager, and the protected onboarding procedure validates the code, binds the account to the correct unit and organization, then allows entry to the tenant portal. The code is never trusted solely from frontend validation; the server verifies its format, ownership, and organization relationship.

The PostgreSQL-first target stores user identity and role records in the `users` table. The independent authentication migration must map the provider’s stable user identifier to `users.openId` or the selected provider identifier field, preserve email and phone values, and maintain organization and unit membership.
