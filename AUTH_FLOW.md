# Maintainr Authentication Flow

Maintainr uses self-hosted email/password authentication backed by PostgreSQL. The public `/sign-in` and `/sign-up` pages submit to local tRPC procedures; they do not redirect to Manus OAuth or any external login portal.

During signup, the server normalizes the email address, hashes the password with Node’s built-in scrypt implementation, and creates a user record with a generated local `openId`. If the email matches the server-only `BOOTSTRAP_MANAGER_EMAIL` value, the first account receives the `PROPERTY_MANAGER` role. Other new accounts default to `TENANT`. Existing invitation records with the same email can be completed by signup without replacing their organization, unit, or assigned role.

Successful authentication creates a random session token. Only its SHA-256 hash is stored in the PostgreSQL `sessions` table. The raw token is delivered through an `httpOnly`, `secure` production cookie with `SameSite=Lax`; it is never returned to browser JavaScript or stored in the frontend. Sessions have an expiry time and are explicitly revocable during logout or password reset. The tRPC context resolves the current user from the session table, and protected procedures remain the authoritative access boundary.

Password reset requests intentionally return the same accepted response whether or not an account exists. When Resend is configured, the server sends a time-limited link containing a single-use token. Only the token hash is stored in `passwordResetTokens`; consuming a valid token updates the password, marks the token as used, and revokes existing sessions. Reset requests and sign-in attempts are rate-limited in the server process. Deployments should use a shared rate-limit service if multiple server instances are introduced.

After authentication, the exact role is checked by the protected portal route guard. The backend remains authoritative for role, organization, ticket, reminder, and unit scoping; the frontend guard only prevents confusing navigation. A user without the required portal role receives an access message rather than seeing another role’s workspace. Role-specific routes remain `/manager`, `/tenant`, `/technician`, and `/owner`.

First-time tenants use `/join-unit` after authentication. The tenant enters the six-digit access code generated by a property manager, and the protected onboarding procedure validates the code, binds the account to the correct unit and organization, then allows entry to the tenant portal. The code is never trusted solely from frontend validation; the server verifies its format and database match.

The PostgreSQL-first schema includes `users.passwordHash`, `sessions`, and `passwordResetTokens`. Import `POSTGRESQL_SCHEMA.sql` before the first signup. Keep `DATABASE_URL`, `BOOTSTRAP_MANAGER_EMAIL`, `AUTH_BASE_URL`, Resend credentials, and all provider secrets in the deployment provider’s server-side secret manager. Do not expose them through `VITE_` variables, React code, or public files.
